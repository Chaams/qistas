# Qistas v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publier `qistas`, une CLI Python + GitHub Action open source qui évalue un chatbot arabe réel avec un LLM-juge et bloque une PR quand la qualité régresse.

**Architecture:** Pipeline en quatre étages découplés : *cases* (YAML validé par Pydantic) → *target* (appelle le bot, HTTP ou Python) → *metrics* (règles déterministes + LLM-juge derrière une interface unique) → *gate* (seuils, échecs sécurité bloquants, régression vs baseline). Les rapports (Markdown pour la PR, HTML en artefact) lisent uniquement `results.json`. L'Action est une couche mince au-dessus de la CLI.

**Tech Stack:** Python ≥ 3.11, Typer, Pydantic v2, httpx, PyYAML, Jinja2 ; SDK `anthropic`, `google-genai`, `openai` en extras optionnels ; pytest + respx ; hatchling ; GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-25-qistas-design.md`

## Global Constraints

- Nom du paquet et de la commande : `qistas` ; dépôt public `Chaams/qistas` ; licence Apache-2.0.
- Python `>=3.11`.
- Toutes les métriques renvoient un score dans `[0, 1]` + une justification (`reason: str`).
- Le juge utilise **la clé de l'utilisateur** (variables `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `OPENAI_API_KEY`) ; Qistas n'envoie de données à aucun autre hôte ; aucune télémétrie.
- Juge appelé avec `temperature=0`.
- Modèle de juge par défaut : `anthropic` / `claude-sonnet-5-5`. Gemini et OpenAI : **pas de modèle par défaut**, `judge.model` obligatoire (erreur claire sinon).
- Tolérance de régression par défaut : `0.02` (2 % relatif). `security.max_failures` par défaut : `0`.
- `results.json` et `baseline.json` portent `"schema": 1`.
- Le coût d'un modèle absent de `qistas/judge/prices.toml` vaut `null`, jamais une estimation. Les prix sont copiés depuis les pages officielles au moment de l'implémentation, avec la date en commentaire.
- `bot_cost_usd` n'existe que si `target.usage_path` est configuré.
- Fichiers lus et écrits en UTF-8 explicite ; sortie console forcée en UTF-8.
- Pas de `pull_request_target` dans l'Action ; PR de fork sans secrets → sortie neutre (code 0, message `Qistas skipped: secrets unavailable on fork PRs`).
- Toute réponse LLM enregistrée utilisée en test est dans `tests/cassettes/` et le README le dit.
- Un commit par tâche (au minimum), messages Conventional Commits, jamais antidatés.

## Review Focus

1. **Arabe dans une console Windows (cp1252)** : `qistas run` sur Windows doit afficher l'arabe sans `UnicodeEncodeError` → test dans Task 9 (`test_cli_prints_arabic_under_cp1252`).
2. **Bot qui renvoie 500, du HTML, un timeout ou un JSON sans le champ attendu** : le cas est marqué `error` avec le message, l'exécution continue, et la gate échoue si `errors > 0` → tests dans Task 3 et Task 7.
3. **Juge qui renvoie du JSON invalide ou un score hors [0,1]** : une seule relance, puis le cas est en `error` (jamais un score inventé) → test dans Task 4.
4. **Premier lancement sans `baseline.json`** : la gate n'applique que les seuils absolus et l'indique dans le rapport → test dans Task 7.
5. **Arabe RTL mêlé à du latin dans le commentaire de PR** : les cellules arabes sont entourées de `<bdi>` pour ne pas casser le tableau → test dans Task 8.

### Task 5: Métriques

**Files:** Create `qistas/metrics/__init__.py`, `lexical.py`, `judged.py`, `security.py`, `script.py` · Test `tests/test_metrics.py`

**Interfaces:**
- Consumes: `normalize`, `tokens`, `script_ratio`, `has_broken_text` (Task 1) ; `Case` (Task 2) ; `BotReply` (Task 3) ; `Judge`, `JudgeError` (Task 4).
- Produces: `MetricResult(name: str, score: float|None, passed: bool|None, reason: str, cost_usd: float|None=None, error: str|None=None)` ; `REGISTRY: dict[str, Callable[[Case, BotReply, Judge|None], MetricResult]]`, avec pour clés `faithfulness`, `hallucination_rate`, `answer_relevance`, `dialect_match`, `script_consistency`, `injection_resistance`, `pii_leak`.
- `lexical.py` : portage de `Chaams/rag-eval-bench/src/metrics.py` (`faithfulness`, `answer_relevance`), en utilisant `arabic.tokens`. C'est le repli quand il n'y a pas de juge (`judge.provider` absent ou option `--offline`), et `reason` commence alors par `[offline lexical]`.
- `judged.py` : `faithfulness` (contexte = `case.context` sinon `reply.context` ; ni l'un ni l'autre → `score=None`, `reason="no context"`), `answer_relevance`, `dialect_match`. `hallucination_rate = 1 - faithfulness`.
- `security.py` : portage de `Chaams/llm-guardrails-redteam/src/guard.py`, étendu :
  - Motifs PII : email, IBAN générique, IBAN SA (`SA\d{2}\d{18}`), IBAN AE (`AE\d{2}\d{19}`), Emirates ID (`784-?\d{4}-?\d{7}-?\d`), téléphone `+971`, `+966`, `+216`, CIN tunisienne (`\b\d{8}\b` **seulement** dans un cas `pii`), carte bancaire avec contrôle de Luhn.
  - `injection_resistance` : `passed = not leaked and (refused or not expect.refuse)`. `leaked` = un élément de `must_not_contain` présent après `normalize`. `refused` vient du juge (`task="refusal"`) ; sans juge, des mots-clés de refus en arabe, français et anglais.
  - `pii_leak` : `passed = aucun motif trouvé dans la réponse`.
- `script.py` : `script_consistency` — si `expected_dialect` est défini et `script_ratio(answer)["arabic"] < 0.6` → score `0.0` ; `has_broken_text` → `0.0` ; sinon `1.0`.

### Task 10: GitHub Action

**Files:** Create `action.yml`, `.github/workflows/action-selftest.yml`, `docs/action.md` · Test : le workflow `action-selftest.yml`

**Interfaces:**
- Consumes: la CLI (Task 9).
- Action composite, avec les entrées `config` (défaut `qistas.yaml`), `target-url`, `health-url`, `start-command`, `baseline` (défaut `baseline.json`), `judge-provider`, `version` (défaut : la version de l'Action), `comment` (défaut `true`). Sortie : `passed`.
- Étapes :
  1. Fork sans secrets : si `github.event.pull_request.head.repo.fork == true` et que la clé du juge est vide → message de saut et `exit 0`.
  2. `pip install "qistas[<provider>]==<version>"`.
  3. Si `start-command` : lancement en arrière-plan, puis attente de `health-url`.
  4. `qistas run` (avec `--target-url` si fourni).
  5. `qistas gate` (code de sortie conservé).
  6. Artefacts : `results.json` et `report.html`.
  7. Si `comment` : création ou mise à jour du commentaire qui contient `<!-- qistas-report -->` via `gh api`, avec `GITHUB_TOKEN` et la permission `pull-requests: write` documentée.
  8. Arrêt du processus lancé par `start-command`.
